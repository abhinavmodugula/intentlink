IntentLink — Architecture

A chat prompt becomes a reshaped page

One Chrome extension, a per-site adapter for each store, and a swappable rank engine (DeepSeek, Jev, or a zero-network fallback) that decides what to highlight. No chat UI of its own, no backend server — the chat is whatever you already use.

The end-to-end flow

From a typed request to a reshaped page, in six steps.

User types intent

In ChatGPT or Claude — "noise-cancelling headphones under $100, good for flights."

2

A markdown link: the site's search URL plus the prompt in the URL fragment.

→
3

Click opens the real site

Chrome navigates normally. The fragment never reaches the site's server.

→
4

Adapter extracts items

A per-site content script reads ~20–30 results or facts straight from the DOM.

→
5

Rank engine decides

One call — DeepSeek, Jev, or a local fallback — returns keep/dim decisions.

→
6

Page reshapes

Matches highlighted, clutter dimmed/hidden — same page, same cart, same checkout.

From ChatGPT to an IntentLink

No new syntax to learn, and no code on the chat side — a Custom GPT / Claude Project is just given instructions for how to build the link. The intent is plain, URL-encoded natural language in the fragment; there's no rigid schema to fill in.

https://www.amazon.com/s?k=noise+cancelling+headphones#ll-intent=noise%20cancelling%20headphones%20under%20%24100%2C%20good%20for%20flights

site URL — built from the key product words, so the page loads real results even before the extension does anything —  #ll-intent= — the marker the content script looks for —  encoded intent — the shopper's full original request, untouched.

The chat-side instructions, verbatim (chat/gpt-instructions.md):

1. Pick the site (default amazon.com). Build its search URL from the key
   product words: https://www.amazon.com/s?k=<words joined by +>
   If the user pasted a product URL, use that URL instead.
2. Append #ll-intent= followed by the user's full request, URL-encoded.
3. Reply with one markdown link titled "Open on Amazon, shaped for you"
   and nothing else.

Because the intent lives in the URL fragment (everything after #), it's never sent to the site's server — browsers simply don't transmit fragments in HTTP requests. It's a client-side-only handoff by construction, not by policy.

Per-site adapters: precomputed, not guessed live

The PRD's original vision was a frontier model that compiles a site's selectors once, automatically. What's actually running is the hand-verified version of that same idea: each site gets a small adapter file that knows how to read that site's DOM — written against real markup, not assumed, then committed and shipped with the extension. No model call happens just to read a page; the only network call is the one rank() decision per reshape.

SiteShapeHow the selectors were verified
Amazon Search results + product page Known, well-documented result/PDP structure; several selector fallbacks per field.
Craigslist Search results + posting Fetched directly via curl — no bot-wall. Clean, unhashed, hand-authored class names (.cl-static-search-result, .attrgroup .attr) sampled across 360 live listings.
OpenTable Restaurant page Blocked by Akamai for direct fetch — built on schema.org Restaurant JSON-LD instead, which needs zero site-specific selectors at all.
Uniqlo Search results Also Akamai-blocked. Calibrated by running a diagnostic snippet in the user's own browser DevTools and iterating against the real, returned DOM signatures.

Every adapter exposes the same tiny contract — window.LL_ADAPTER = { extract(), clutterSelectors, pageType } — so the rest of the pipeline (two-pass reshape, rank dispatch, refine, reset, best-match promotion) is written once and never has to know which site it's running on.

Rank engines — one contract, three implementations

Every engine implements rank(intent, items) → {filters, summary, keep}, switched in one place. The page never waits on a model: an instant local pass runs first, then whichever engine is active refines it.

default  DeepSeek

One JSON-mode chat completion. Given the schema and the extracted items, it returns which ids to keep and a short reason for each — genuine generated prose.

No per-item confidence score, so every kept item renders as a full, confident highlight.

optional  Jev

TypeSafe's "System One" model — one noul (calibrated 0–1 probability) question per item, answered in parallel in a single call.

The probability drives the highlight strength directly: ≥0.8 is a confident match, 0.3–0.8 a lighter "maybe," below that it's dimmed. Can't write prose, so reason text is assembled from parsed constraints instead of model-generated phrases.

fallback  Heuristic

Pure JS — regex-parsed price/rating/prime constraints plus keyword overlap. No network call at all.

Runs whenever a model call errors, times out past 4s, or DEMO_MODE is on — guarantees the page never shows a blank or broken reshape.

What keeps this honest

A handful of rules carried through every engine and every adapter:

  • Deterministic re-check (F6). After any engine returns, plain JS drops any kept item that actually violates a parsed constraint (price, rating, Prime) — a model mistake can never highlight something that breaks the shopper's own stated limit.
  • Two passes, same classes. An instant, model-free pass dims clutter and provable constraint failures the moment items are extracted; the model-refined pass only narrows further. A slow or failed model call just leaves the instant pass's result standing.
  • One best match, always chosen from what already matched. The top-scoring kept item gets a badge and is promoted first — but it's picked from the plan's own keep list, never overriding a filter to force a result.
  • The real page, never rewritten. Reshaping only toggles CSS classes and adds small UI (a summary bar, an answer card) — the site's own HTML, cart, and checkout are untouched.
