The Intent Router URL

https://www.amazon.com/s?k=noise+cancelling+headphones#ll-intent=noise%20cancelling%20headphones%20under%20%24100%2C%20good%20for%20flights
site URL — real results load instantly #ll-intent= — marker the content script looks for encoded intent — the shopper's request, untouched
🔒 Lives in the URL fragment (after #) — browsers never send fragments to the server. Client-side-only by construction, not by policy.

Chat-side instructions, verbatim — chat/gpt-instructions.md:

1. Pick the site (default amazon.com). Build its search URL from the key
   product words: https://www.amazon.com/s?k=<words joined by +>
   If the user pasted a product URL, use that URL instead.
2. Append #ll-intent= followed by the user's full request, URL-encoded.
3. Reply with one markdown link titled "Open on Amazon, shaped for you"
   and nothing else.

Per-site adapters

Precomputed selectors, verified against real markup — not guessed live, no model call just to read a page.

SiteShapeVerified via
Amazon Search + product page Well-documented DOM; fallback selectors per field.
Craigslist Search + posting Direct curl, no bot-wall — sampled 360 live listings.
OpenTable Restaurant page Akamai-blocked → read schema.org Restaurant JSON-LD instead.
Uniqlo Search results Akamai-blocked → calibrated live via DevTools diagnostics.

Every adapter exposes one contract — window.LL_ADAPTER = { extract(), clutterSelectors, pageType } — so the pipeline never needs to know which site it's on.

Rank engine — Jev

One contract — rank(intent, items) → {filters, summary, keep} — implemented by TypeSafe's Jev, a typed-inference model that only answers calibrated probability questions. It can't write a word of prose.

🎯  The question

  • One noul (0–1 probability) question per item.
  • Every item answered in parallel, in a single call.

📊  The mapping

  • ≥0.8 → confident match.
  • 0.3–0.8 → lighter "maybe."
  • Below 0.3 → dimmed.

🔒  The constraint

  • Can't generate prose — only a probability.
  • Reason text assembled from parsed constraints, never model-written.

What keeps this honest

  • Deterministic re-check (F6). Plain JS drops any kept item that violates a parsed constraint — a model mistake can't break the shopper's own stated limit.
  • Two passes, same classes. An instant, model-free pass runs first; the model only narrows further. A slow/failed call leaves the instant pass standing.
  • Best match, chosen from what already matched. Badge goes to the top-scoring item already in the keep list — never a filter override.
  • The real page, never rewritten. Only CSS classes + small UI toggle. Site HTML, cart, and checkout are untouched.
